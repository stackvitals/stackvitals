# What leaves your repo

StackVitals runs in your own workflow and keeps its history in your repo. There is no StackVitals server: nothing is sent to us. This page lists everything a run (or the app) sends anywhere, built from the code's own list, and a test fails if the code gains an outside host this page doesn't name.

| Feature | Goes to | What is sent | When | To turn it off |
|---|---|---|---|---|
| Every module (reading your repo, writing its results) | api.github.com, github.com | Requests with the workflow's own token: it reads runs, logs, pull requests, issues and files of this repo, and writes the stackvitals-data branch, Pages, and the comments, labels and issues your switches allow. | every run | Stays inside GitHub; remove a module from `modules` to stop it. |
| Delivery from Bitbucket or Azure DevOps (command line) | api.bitbucket.org, dev.azure.com | Read-only requests for the repo you name, with BITBUCKET_TOKEN or AZURE_DEVOPS_TOKEN when set; nothing about a GitHub repo. | only when you run `stackvitals delivery --bitbucket` or `--azure` | Don't run it. |
| SonarQube or SonarCloud code quality | sonarcloud.io | The Sonar project key in [connectors.sonar] (and the SONAR_TOKEN when set), to read its quality gate and measures. | once a day, when a project is set | Leave project under [connectors.sonar] empty. |
| Security checks: the OpenSSF Best Practices badge | www.bestpractices.dev | A public repo's address, to look up its badge level; a private repo's is never sent. | once a week | Remove `deps` from `modules`. |
| Benchmarks from public repos | github.com | A download of the crawl's benchmark files from stackvitals/stackvitals's releases; nothing about your repo is sent. | every run, cached a day | Nothing to turn off: it is a download. |
| Shared benchmark figures (opt-in) | github.com | An issue on stackvitals/stackvitals, filed by a person from a link in the run summary: this repo's rounded CI figures, its language and star tier, a random id kept in the data branch, and its name only with `name = true`. It is public once filed, and shows the account that filed it. | only when someone files the link | `[benchmarks] share = false` (the default); close the issue to withdraw it. |
| Dependency licences and Scorecards | api.deps.dev, api.scorecard.dev | The name and version of every package in the dependency graph (to deps.dev; that includes the names of private or internal packages the graph lists) and the public source repos behind them (to OpenSSF Scorecard); never this repo's name. | weekly, Dependencies module | `[deps] outside_lookups = false`. |
| Known vulnerabilities in every lockfile | github.com, api.osv.dev, api.deps.dev, osv-vulnerabilities.storage.googleapis.com | A download of the pinned OSV-Scanner from its GitHub release (checked against its SHA-256); then the name and version of every package in the repo's lockfiles to OSV (and, for manifests without exact versions, to deps.dev to resolve them). With outside lookups off, OSV's public databases are downloaded instead and no package name is sent. | after CI runs and on the schedule, at most every 6 hours unless a lockfile changed; Dependencies module | `[deps] outside_lookups = false` (scans offline). |
| Release checks on changed packages | registry.npmjs.org, pypi.org, api.deps.dev | The name and the old and new versions of each npm or PyPI package a pull request adds or upgrades (at most 30), to read when it was released, its install scripts, dependencies and build provenance. | pull requests that change a lockfile | `[deps] outside_lookups = false`. |
| Runtime versions | endoflife.date | Only the runtime's name (nodejs, python, php, ruby or go), to read its release lines and support dates; never the repo or its versions. | weekly, Dependencies module | `[deps] outside_lookups = false`. |
| GuardDog code check (opt-in) | pypi.org, files.pythonhosted.org, registry.npmjs.org | Downloads of GuardDog itself and of each npm or PyPI package version a pull request adds or upgrades (at most 10), whose code it reads on the runner; nothing about the repo is sent. | pull requests that change a lockfile, only with `[deps] guarddog = true` | Off by default. |
| History in a bucket (opt-in) | the s3-endpoint you set | Every file of the data branch (history, pages, decisions), signed with your bucket key, to your own bucket. | every run, only with `storage: s3://...` | The default, `storage: git`. |
| Look-alike package check | api.npmjs.org, pypistats.org | Only the name of a package a pull request adds whose name is one edit from a popular one, to read its weekly downloads. | pull requests that change a lockfile | `[deps] outside_lookups = false` (names are still checked). |
| Model triage of unexplained CI failures | api.anthropic.com, api.groq.com, api.mistral.ai, api.openai.com, generativelanguage.googleapis.com, the `url` you set under [ci.triage] | The failing step's log excerpt (bounded) and the changed files' names, with your key, to the provider you choose or the endpoint you set; at most 3 calls a run. | off until `[ci.triage]` and a key are set; a private repo also needs `allow_private = true` | Off by default. |
| Issue trackers and incident tools | *.atlassian.net, api.linear.app, api.pagerduty.com, api.incident.io | Requests with your key that read issues, sprints and incidents; with write-back on, a comment linking the merged pull request (and a status move). | only with a key in the workflow; write-back only with `write_back = true` | Remove the key. |
| A Discourse forum | your forum's host | Read requests for its public topics, with no key; only times and flags are kept, never usernames or text. | only with url under [connectors.discourse] | Remove the url. |
| Slack and Discord support channels | slack.com, discord.com | Read requests with your bot token for the channels you name; only times and flags are kept, never text or user ids. | only with a slack-token or discord-token | Remove the token. |
| Copilot usage reports | api.github.com, the report file host GitHub names | Requests with the reports token; the report file is fetched without it. | only with the Copilot token | Remove the token. |
| AI spend | api.anthropic.com, api.openai.com, api.cursor.com | Read-only cost and usage report requests, each with that provider's own admin key; nothing about the repo. | only with an AI spend admin key | Remove the key. |
| Chat alerts and the weekly digest | your webhook's host (Slack, Teams, Discord, other) | Alert and digest text: metric names and values, test names, this repo's name, links to its pages. | only with a webhook secret | Remove the webhook. |
| Test connection | each connector's own host (above), your webhook's host, the s3-endpoint you set, your model provider, your GitLab host (`CI_API_V4_URL`) | One cheap call per connector asked for, with its own key: it reads one item, never writes to a tracker. A chat webhook gets one labelled test message ("StackVitals connection test"), never retried; a bucket gets one small object (`.stackvitals-check`) written and deleted under the prefix; model triage calls the provider's model list; GitLab reads the project and the token's own scopes, at `CI_API_V4_URL` for a self-hosted GitLab. The results go in docs/connectors.json; on a public repo without account, channel, team or bucket names. | only when someone with write access presses Test connection, comments `/stackvitals check`, or runs `stackvitals connectors check` | Don't run it. |
| Exports (DevLake, CTRF, Postgres, OpenTelemetry) | api.github.com | Reads with your token; the files are written on your machine and sent nowhere. | only when you run `stackvitals export` | Don't run it. |
| Portal Scorecard checks | api.scorecard.dev | The names of the organisation's public repos; private repos are never sent. | weekly, Portal module | Leave the Portal module out. |
| GitLab CI | gitlab.com | Requests with your GitLab token for one project's pipelines and jobs. The GitLab job also writes the project's stackvitals-data branch, its Pages and one merge request note, and downloads StackVitals from github.com and its packages from PyPI. | when you run `stackvitals ci gitlab`, or each pipeline once you include the GitLab job | Don't run or include it. |
| The app in a viewer's browser | your Pages site, api.github.com, raw.githubusercontent.com, avatars.githubusercontent.com, api.linear.app, your sign-in relay (optional), cdn.jsdelivr.net, cdnjs.cloudflare.com | The viewer's browser loads the app from your Pages site (its code, font and docs are all there). With a GitHub token or sign-in, the app calls api.github.com with it to read repos and data branches, set up the workflow, save settings and decisions, and save secrets sealed in the browser; workflow files and data are also read from raw.githubusercontent.com, and the account picture from avatars.githubusercontent.com. Testing a Linear key from the page sends it only to api.linear.app. Sign in with GitHub, when the site was built with a relay, sends the one-time code (and later the refresh token) to that relay, which swaps it for a token and keeps nothing. Explore loads DuckDB from jsDelivr; printable pages load Chart.js from cdnjs. Nothing goes to a server of ours. | when someone opens the app | Keep Pages private, or don't publish them; don't connect GitHub in the app. |

## Nothing leaves GitHub

Leave model triage, connectors and webhooks unset (they are, by default), and set `[deps] outside_lookups = false`. Runs then talk to GitHub only: your repo, and the benchmark download from public releases. A private repo's Pages are private on plans that allow it; otherwise publish none and read the job summary and the data branch.

## What each token can reach

- **The workflow token** (`GITHUB_TOKEN`): this repo only, with the permissions the workflow file grants.
- **An optional personal or App token** (`stackvitals-token`): whatever it was granted; the Portal's App is read-only.
- **Tracker and incident keys:** only their own service's host; the Jira key goes only to an `*.atlassian.net` site.
- **A model key:** its provider's host, or the `url` you set under `[ci.triage]`.
